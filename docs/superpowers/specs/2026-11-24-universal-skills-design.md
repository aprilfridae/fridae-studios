# Universal skills: one library every AI uses, found by search, one copy of each

Asked for by the user on 2026-11-24:
- "i want it to be bundled with a shitload of really useful skills. thats sort of the whole point."
- "i want it to also upload new skills generated by people so its basically one huge Vault of skills and guides and
  notes so AI agents can just WORK."
- "make it so every model can use every other models skill. make it so all skills are universal. make it so skills are
  bundled. make it so skills are called efficiently and make sure that there are no duplicate skills. there should
  basically be like . 1 Source of truth for each skill, and the better one wins out over duplicates. same as notes."

The user approved these decisions in the conversation, after a second opinion they pasted in:
- An AI recommends the winner between duplicates, and a person clicks to accept.
- Skills are found through the search index as pointers ("RAG as a router").
- A small core set is pinned in every agent's instructions.
- Guides and skills become one thing.
- "Bundled" means the library downloads automatically on install.

## Intent

Fridae agents on any AI (Claude, Gemini, Cursor, OpenCode, Codex), in game and plain projects, can just work: the
right know-how for the task is at hand without the user setting anything up, without paying for a long list on every
turn, and without two competing versions of the same instructions.

## What exists today

- **Guides.** About 30 hand-listed guides in `rbxkit_mcp.py` (`GUIDES`), loaded by name with `rbx_guide`.
  - Their names and descriptions are in every agent's instructions.
  - They are also indexed by the search (the knowledge exam found the right guide on 8 of 8 guide questions).
  - Several are converted Claude skills (`redesign-skill`, `soft-skill`, ...). They are Roblox-leaning.
- **Branch `feature/shared-skills`** (`fb64721`, worktree `/Users/angela/fridae-skills`, not merged).
  - `rbxskills.py` finds the user's skills in Claude Code's folders, plugins, what the Claude apps synced, other tools'
    folders and the project.
  - A new `rbx_skill` tool (list, load, read) serves them to every AI.
  - Every agent's instructions carry a one-line-per-skill catalog (64 skills today).
  - Cursor was tested live, OpenCode partly, Gemini not.
  - Details are in its `DEVELOPING.md`, "Skills for every AI".
- **Notes.** Notes are searched through `rbx_vault` (Light hybrid index by default).
- **Unified vault design** (`2026-11-24-unified-knowledge-vault-design.md`, approved, not built):
  - one portable `Knowledge/` folder;
  - the vault as an automatic download whose updates never override the user's own files;
  - community submissions as GitHub pull requests the maintainer reviews in a Submissions inbox.

## Goals

1. **One kind of thing.** A skill is a folder with a `SKILL.md` and any files or scripts it needs. Today's guides and
   Fridae's role instructions become skills.
2. **Universal.** Every skill works on every AI through Fridae's own tool server, which every AI already gets.
3. **Efficient.** What every turn costs does not grow with the size of the library.
4. **One source of truth.** Each skill exists once in the library an agent sees. When two overlap, the better one wins
   (or they are merged), by a person's click on an AI's recommendation. The same goes for notes.
5. **Bundled and growing.** A large starter library arrives with the install. People's own skills come back as
   submissions, and accepted ones reach everyone through updates.

## Non-goals

- Changing how Claude Code itself loads skills, or editing the user's `~/.claude`, `~/.gemini`, `~/.cursor` or
  OpenCode config. Fridae reads those folders; it never writes them.
- A marketplace, ratings by strangers, or skills that install without review.
- Running skill scripts on the app's own initiative.

## Anti-goals (a failure even if it works)

- An agent sees two versions of the same skill.
- A community skill reaches anyone's Fridae without the maintainer's review.
- A skill whose licence does not allow sharing is shipped or submitted.
- The cost of every turn climbs as the library grows.
- One of the user's own skills or notes is lost or silently overwritten.

## The skill format

A folder `<name>/` holding `SKILL.md` (the Claude/Agent Skills format) plus optional `references/`, `scripts/` and
assets. Front matter:

| field | meaning |
|---|---|
| `name` | its one identity, lowercase-dashed; a plugin's skill keeps `plugin:skill` |
| `description` | what it does and when to use it (the search reads this first) |
| `examples` | 3–8 example tasks it is for (the search reads these too) |
| `applies` | `game`, `plain` or `both` (default `both`) |
| `core` | `true` pins it in every agent's instructions (see Loading) |
| `owner` | `app` (Fridae's own; never replaced by a submission), `shipped`, `community`, `user` |
| `source`, `licence` | where it came from and under what licence; required for `shipped` and `community` |
| `supersedes` | names it replaced (the exam showed this mark works perfectly for notes) |
| `updated` | date of the last change |

Claude-specific mentions (ToolSearch, the Skill tool, `${CLAUDE_SKILL_DIR}`) are allowed. `rbx_skill load` fills the
paths and adds the note today's guides carry ("Mentions of ToolSearch or skills are Claude Code details you can
ignore").

## Where skills live: one library

- **Shipped and community skills:** `vault/Skills/<name>/` in the app's vault today. Once the unified vault is built,
  they move to `Knowledge/Skills/<name>/`, delivered by the vault download.
- **The user's own skills:** `~/Documents/Fridae Studios/skills/<name>/` today. They move to `Knowledge/Skills/` with
  the unified vault move.
- **Fridae's own skills stay inside the app** (my call, keeping the unified vault design's rule that the app's own
  instructions are app internals).
  - The role instructions (workflow, studio/Lead, critic, tester, producer, promo) name tools and flows that change
    with each release, and the Rust code leans on them (`routing.txt`, the kickoffs, the team folder). So they get
    `owner: app`, ship read-only inside the app, version with it and work offline.
  - They are in the same library, search shelf and `rbx_skill` as everything else, and can't be edited, replaced or
    submitted. The Studio team's expert notes (`vault/Fridae/Team/`) stay app internals and do not become skills.
- **Today's other guides** (design styles, game design, economy, sound and so on) are content. They become `shipped`
  skills in `vault/Skills/<name>/` and later travel with the vault download, like the starter library.
- **Skills in other places** (Claude Code's folders and plugins, the Claude apps' synced skills, `~/.agents`,
  `~/.codex`, `~/.cursor`, `~/.gemini`, OpenCode's, a project's `.claude/skills` and `.agents/skills`, as
  `rbxskills.py` finds them) are **import sources**, not a second library:
  - On first sight, an imported skill is copied into the user's library with `owner: user` and its `source` (path, plus
    a hash of the folder).
  - When the source changes later and the user's copy was not edited, the copy is refreshed. When both changed, the
    vault update rules apply (keep the user's, save the new one beside it, flag it in Review).
  - A project's own skills stay with the project (like game-only notes) and are not copied out.
  - The seven Claude-desktop-only skills (`APP_ONLY` on the branch) are never imported.
- **Claude agents see the library, not their own copies** (my call).
  - Fridae runs Claude in account folders of its own (`accounts.rs`), which today link the user's `~/.claude/skills`.
    Instead of that link, Fridae builds that folder's `skills` from the library's winners, as links to them. The user's
    `~/.claude` is never touched.
  - Claude Code plugins (superpowers and so on) still list their own skills, and Fridae doesn't switch them off.
  - When a library skill is the same skill as a plugin's (known through the import link or the overlap check): if the
    library's copy is the plugin's unchanged, Fridae leaves it out of pins and suggestions, so Claude sees it once.
  - If the library's winner differs (merged or replaced), Fridae pins or suggests its own, and Claude's instructions
    say: "When a Fridae skill (rbx_skill) and a Claude Code skill cover the same thing, use the Fridae one."
  - This is the one place two versions can show up, and only for Claude with that plugin enabled.

## No duplicates, the better one wins

- **Identity.** One name, one skill. An `owner: app` skill always keeps its name.
- **Overlap check.** Before a skill joins the library (import, shipped update or accepted submission), the search
  compares its name, description and examples with the library's.
  - **Copies that are clearly the same settle by themselves** (my call): same upstream source and the same content
    hash, or byte-identical. The newest one becomes the library's copy and the others become its import links. No card.
  - **While a card is open, nothing stops working** (my call): the skill already in use stays in use, and the newcomer
    waits. On first run, an import that would open many cards opens one **bulk review** list instead (one row per
    pair, with the recommendation, and Accept all recommendations).
  - Otherwise, above a threshold, it does not join yet. A **Review card** shows both: what each covers, scripts and files, source,
    licence, last change and how often each was loaded here.
  - A cheap model writes a recommendation (my call on who): a cheap OpenCode model (DeepSeek/GLM) when the user has
    OpenCode, otherwise the user's default AI on its lowest effort, and with no AI connected, the card shows the two
    side by side without a recommendation. The recommendation is: keep the
    existing one, replace it, or merge them, with a one-paragraph why and, for a merge, the merged `SKILL.md`.
  - The user clicks Keep / Replace / Merge / Keep both (Keep both renames the newcomer). The loser is not deleted: it
    goes to `Skills/.replaced/` with a `supersedes` mark on the winner, and can be put back from the card's history.
- **What "better" means to the recommender:** covers more of the real task; specific and correct (checked against the
  vault notes where it states facts); scripts that run; newer; an open licence; loaded more often here. Loads are a hint
  only.
- **Notes, the same way.**
  - Notes already join an existing note rather than near-copy it ("Learned in Fridae").
  - The same overlap check runs on notes from shipped updates and accepted submissions.
  - A vault-upkeep pass flags near-duplicate or contradicting notes as Review cards with a recommendation, using the
    same check and recommender as skills. It runs once a week while the app is open and idle, and on demand from
    Setup. The exam found one ready test case: heavy-hit freeze, 80–150 ms against 66 ms.
- **The maintainer's Submissions inbox** shows the same comparison and recommendation for a submitted skill or note
  that overlaps the official vault.

## Loading: pinned core plus search as a router

- **Pinned core.** About 12 skills marked `core: true`, filtered by the project's kind (game or plain), appear in every
  agent's instructions as one line each (name and when to use). Starting set (the builder's to adjust):
  - for every project: brainstorming, systematic-debugging, test-driven-development, verification-before-completion,
    writing-plans, ui-ux-pro-max;
  - for game projects: workflow, playtest, ui-design, game-bible, game-design, critic.
- **Everything else is found, not listed.** The instructions carry one line instead of the catalog: other skills are
  found with `rbx_skill search` and the app suggests matches each turn.
- **The search index gets a `skills` shelf.**
  - One entry per skill: name, description, examples and `applies`. Never chunks of the body.
  - A hit returns a pointer ("load with `rbx_skill load <name>`"), the pattern guides already use.
  - Keyword search covers it when the index is off.
- **Per-turn suggestions.** For each user message, the app searches the `skills` shelf with the message (and the
  project's kind) and adds at most 3 matches above a threshold to that turn as one short line: "Skills that may fit: a
  (why), b (why)". This is local, costs no AI tokens, and does not depend on the model remembering to search. Matches
  already pinned, or already loaded in this chat, are left out.
- **`rbx_skill` on the tool server**, every AI: `search`, `load` (SKILL.md with paths filled, its folder and file
  list), `read` (one file inside the skill's folder only), `list` (paged, for browsing).
  - `load` keeps what `rbx_guide` does today, for every skill: an outline instead of the whole text for a big skill,
    one section by name, several skills in one call, size caps, `name/reference` for a file in `references/`, and the
    credit and web-guide notes.
  - `rbx_guide` stays as another name for `rbx_skill load`, so existing instructions and habits keep working.
  - `rbx_vault` search results may also point at a skill when one matches, so an agent searching notes still finds it.
- **Scripts** in a skill are run by the agent like any other command, under the chat's normal permission rules. The
  app never runs them by itself.

## Bundled: the starter library

- **Delivery.** It arrives with the vault download on first launch and gets new and updated skills through the vault
  update, which never overrides the user's edits. Until the download is built, it ships inside the app's `vault/` as
  today.
- **Contents:**
  - today's guides, converted;
  - open-licensed skill collections, each checked one by one before it goes in. Candidates: superpowers (MIT),
    ui-ux-pro-max, roblox-dev, design-superpowers and other public collections the user names.
- **Licence rule.** A skill ships only if its licence allows redistribution, and `source` and `licence` are recorded.
  Anthropic's document skills (Word, PDF, Excel, PowerPoint) are not open-licensed: they are never shipped or
  submitted. A user who has them can still use them locally through import.
- **Size.** As many as the licences and the overlap check allow. Duplicates inside the starter set are settled by the
  maintainer with the same Review flow before release.

## Contributing skills

- Skills ride the community submissions in the unified vault design: opt-in (Off / Review each batch / Send
  automatically), a GitHub pull request per batch to the vault repo, and the maintainer's Submissions inbox.
- **What can be sent:** skills with `owner: user` the user made or that an agent wrote in Fridae.
- **Never sent:**
  - imported skills whose source is someone else's collection (they are credited upstream instead);
  - `APP_ONLY` skills and anything without an open licence;
  - project skills.
- **Licence of a submission.** The contributor agrees to CC BY 4.0 for text and MIT for scripts (the inbox shows
  this).
- **The inbox puts scripts first.** A skill with scripts shows its code before anything else, marked "runs on
  everyone's Mac: read it". Nothing a submission says is followed as an instruction by the reviewing AI.
- Accepted skills get `owner: community` and their contributor's credit, and go out in the next vault release.
